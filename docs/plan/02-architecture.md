# Architecture and shared contracts

This is a proposed implementation contract, not existing code. Keep these names consistent across packets. Reuse native Godot features; do not introduce a general ECS, event bus, command serialization framework, inventory plugin, or dependency injection container.

## Engine and scene structure

Use typed GDScript and native scene composition. Player input, movement, carrying and interaction are separate child components; `player.gd` wires them and passes values. Small item scenes need only a visual root, physics shape and item script; do not give each of 5,700 objects dozens of components or per-frame scripts. Use typed exports or scene-unique names for dependencies, signals upward and methods downward. Definition Resources are immutable at runtime; run records contain mutable state.

```text
scenes/main.tscn                       boot/menu/run lifecycle
  RunRoot (Node; RunSession)           owns current run and domain services
    Beach (Node3D; authored scene)
      Terrain / Buildings / Water / Sections / Slots / SpawnAnchors
    Items (Node3D)                     item views; never the source of totals
    Wildlife (Node3D)                  paths and lightweight visual agents
    Player (CharacterBody3D)
      InputReader / Movement / Interactor / Carry / Swim
      Head / Camera3D / HandRig
    Stations (Node3D)                  sorting, shop, collection controls
    UI (CanvasLayer)                  HUD, modal stack, feedback
```

`RunSession` owns data and injects references into `ItemStore`, `SortingStation`, `PlacementService`, `CollectionService`, `ProgressService` and `SaveService`. These are concrete scripts for real subsystems, not interfaces with speculative implementations. UI settings may live in a single application settings object; there is no global mutable inventory singleton. Switching runs frees the old RunRoot before constructing the new one.

Project folders to create as packets require them:

```text
scenes/{player,world,items,stations,ui,wildlife}/
scripts/{core,data,player,items,world,stations,ui,tools,wildlife}/
data/{items,tools,upgrades,world}/
art/synty/                            locally staged selected vendor dependencies
art/placeholders/                     small project-owned coloured cube scenes
shaders/                              project-owned effects only
tools/stage_assets.gd                 explicit editor/offline staging script
tests/run_checks.gd                   one headless test entry point
tests/scenes/                         only needed visual/physics fixtures
docs/handoffs/                        one completed handoff per packet
```

## Definitions and run records

P02 owns the initial types. Extend an existing type when later packets require fields; update its version/serialization together. IDs are strings, never Node instance IDs, array positions or node names generated by the engine.

| Type / file | Required fields and meaning |
|---|---|
| `ItemDefinition`, `scripts/data/item_definition.gd` | `definition_id`, display name, `kind` (WASTE/PROP/VALUABLE), `waste_category` (PMD/ORGANIC/GENERAL/GLASS/NONE), material tags, sorting family, visual scene path, simple collision profile, hand cost (1/2), float/sink mode, required tool, base sale value, eligible spawn tags. Art variations do not change sorting family. |
| `ToolDefinition`, `scripts/data/tool_definition.gd` | Stable tool ID, name, scene, handheld/passive, allowed target tags, range/radius, use interval, shop price, upgrade prerequisite. A delay between vacuum ticks is an animation/throughput rate, not a battery or limited-use cooldown. |
| `UpgradeDefinition`, `scripts/data/upgrade_definition.gd` | ID, level, price, prerequisite, shop/booklet source, affected stat and exact value. Values replace level values instead of multiplying repeatedly on load. |
| `BeachDefinition`, `scripts/data/beach_definition.gd` | Beach/version IDs, scene, ordered sections, budgets, slot inventories, spawn anchor resource, recovery anchors, restoration recipes and starting state. |
| `RunState`, `scripts/core/run_state.gd` | Schema/game/content/generator versions, run ID, seed text, initial manifest/hash, records by item ID, players, table/bin/bag/container records, recovery piles, section/group states, discovery, optional finds, elapsed active seconds, completion receipt, next runtime bag serial, revision. |
| `ItemRecord`, `scripts/core/item_record.gd` | ID, definition ID, immutable home section/zone, required flag, current location, holder/container/slot ID, last world transform, linear/angular velocity and sleep state, dirty patches remaining, buried/revealed status, rescuer/collector attribution where meaningful. |
| Player record | Stable player key (`local` initially), ordered trash/valuable bag IDs, ordered held object refs, equipped handheld IDs (max 2), active slot, owned tools/gear, upgrade levels, integer money, discoveries, transform/velocity, air remaining and immersion/faint state. |
| Disposal bag record | Runtime ID `bag:000001` etc., declared category, ordered waste item IDs, sealed=true, current location/holder/container/rack slot, world transform, linear/angular velocity and sleep state when WORLD, frozen correct-item count for receipt display. Source categories remain on items; do not replace contents with only a numeric count. |
| Recovery pile record | Stable pile ID, dropped item/bag refs and fallback marker position. Resolve markers from current WORLD members; remove recovered/terminal members and retire empty piles. Persist membership so repeated faint/load neither loses markers nor duplicates their contents. |
| Section/group records | Objective IDs or IDs derived from manifest, required slot-family counts, `reward_claimed`, `restored_once`, current completion. Presentation transition progress can be omitted and replayed to its terminal state on load. |

A group is a logical home-section prop-family goal, e.g. `lounges/chairs`; a shelf is physical storage with a mutable claim. This keeps rewards finite even if the player distributes one family across several shelves. A shelf fill can pulse visually; monetary reward belongs only to the logical group's first completion.

## One item, one location

Use `ItemLocation` enum values with serialized names, not numeric ordinals:

| State | Required ownership |
|---|---|
| `WORLD` | World transform; may be resting, floating or active physics. |
| `BURIED` | Authored anchor/depth; hidden until detector reveals it. |
| `ATTACHED` | Rescue ID and attachment anchor; cannot be poked before knife removal. |
| `BAG` | Exactly one player; ordered within their collection bag. |
| `HELD` | Exactly one player; one or two hand units occupied. |
| `TABLE` | Exactly one station and cell. |
| `BIN` | Exactly one station category bin; correction allowed. |
| `SEALED` | Exactly one disposal bag record; that bag may be on rack, ground, in hands or in a large container. |
| `SLOTTED` | Exactly one compatible physical slot, clean prop only. |
| `COLLECTED` | Waste receipt; terminal, counted complete and never spawned again. |
| `VALUABLE_TRAY` / `SOLD` | Station tray or terminal sale receipt; optional valuables only. |

Transitions: WORLD → BAG for eligible waste/valuables; WORLD or SLOTTED → HELD for reusable props; BAG → WORLD for throws/fainting; HELD → WORLD or SLOTTED; BAG → TABLE on unload; TABLE ↔ BIN until sealed; WORLD → BIN for a valid physical throw through a sorting-bin opening; BIN → SEALED; SEALED → COLLECTED only through collection of its bag. BURIED → WORLD on detector revelation; ATTACHED → BAG or WORLD on knife removal. Valuables move from TABLE to VALUABLE_TRAY, then SOLD. Large collection containers accept sealed bags only; throwing loose litter at those containers does not bypass sealing.

Resting/dynamic/floating are view/physics modes within WORLD, not extra ownership. A pickup/placement travel animation is not a third owner. The destination is committed synchronously first; the visual is temporarily non-interactable and travels to it. If the visual is interrupted by load or scene exit, render the committed destination. Never save tween objects.

Disposal bag locations use their own enum: RACK/WORLD/HELD/CONTAINER/COLLECTED. Their contained item IDs remain SEALED until collection regardless of where the bag is carried. Empty bag packaging does not add required IDs.

## Mutation entry points

Services run on the main simulation thread. Validate all preconditions, then update all affected records synchronously without `await`. Reject invalid input with a small `ActionResult` carrying `ok`, a reason enum, changed IDs and optional receipt. Domain data is never partially changed after a failure. No generic network command system is needed.

One action's commit order is: validate → transfer/update source records → finalize affected progress, group payments, restoration flags and first-finish receipt → increment revision once → publish signals and request autosave. RunSession calls ProgressService directly during finalization once P20 exists; a public `items_changed` listener must not create a second progress transaction. Observers and saves see only the fully finalized state. Defer any action requested by a signal listener until publication finishes. Before P20, the same finalization boundary exists without progress work; keep this a small concrete call path, not a transaction framework.

| Owner | Public method / responsibility |
|---|---|
| `ItemStore` | `try_collect(player_id, item_id)`, `try_hold(player_id, object_ref)`, `try_throw(player_id, spawn_transform, impulse)`; capacity, discovery, ownership, LIFO, no blocked-wall throws. |
| `PlacementService` | `preview_slot(player_id, slot_id)` is read-only; `try_place(player_id, slot_id)` and `try_capture(item_id, slot_id)` share validation. `try_remove` updates occupancy, claims and current progress. |
| Cleaning tool | `try_clean(player_id, item_id, patch_id)` changes one dirty patch or transfers an existing standalone residue ID into the bag. Cannot clean through geometry or spend nonexistent capacity. |
| `SortingStation` | `try_unload(player_id)`, `try_sort(item_id, category)`, `try_unsort(item_id)`, `try_seal(category)`, `try_sell_valuable(item_id)`. Sort accepts validated TABLE/BIN sources or a WORLD source physically entering that station's bin opening. All UI and physical bin catches use these methods. |
| Container | `try_deposit_bag(player_id, bag_id, container_id)` / physical capture variant; validate declared category and bag existence. Bags can be picked back up until collection locks them. |
| `CollectionService` | `try_collect_containers(player_id)` builds one receipt, marks eligible contents COLLECTED, marks bags consumed and credits integer money together. Repeat calls find nothing eligible. |
| Shop/booklet | `try_purchase(player_id, upgrade_id)` / `try_equip(player_id, tool_id, slot)`; validate price/prerequisites/source/capacity. No client or UI-supplied price. |
| Swim | `try_faint(player_id)` snapshots all carried refs and releases them once before moving the player to safety. |
| Rescue | `try_cut(player_id, rescue_id, attachment_id)` removes one real attachment and releases the animal after its final attachment. |
| `ProgressService` | Finalize changed IDs inside the initiating action's commit: recompute affected counts/groups/sections, pay first-time group rewards, latch restoration/completion and return notifications for publication afterward. Never infer credit from node deletion. |

`object_ref` distinguishes reusable item IDs from disposal bag IDs. Use a concrete small record with kind/id, not IDs that ambiguously point to different tables. Signals include `items_changed(ids)`, `hands_changed(player_id)`, `wallet_changed(player_id)`, `group_completed(group_id, first_time)`, `section_restored(section_id)`, `run_completed(receipt)` and `save_requested`. Subscribers only update views or request another explicit service action after publication. A snapshot requested from any of these signals must already contain the action's rewards, restoration and finish receipt.

## Invariants that every feature preserves

1. Every manifest ID has exactly one valid record/location. Required waste IDs are never replaced by a new trash ID during cleaning, cutting, throwing or recovery.
2. Bag/hand/table/bin/slot lists agree with each record's owner. Full capacity never deletes an item. Corrections and physical catch use identical rules.
3. Money is a nonnegative integer. Payments and reward flags change in one transaction; presentation repeats cannot pay again.
4. Waste completion equals required records in COLLECTED. Prop completion equals required clean SLOTTED records. Optional valuables, equipment and disposal bags do not change 5,700.
5. Required totals come from the immutable manifest, never from current scene counts. Remaining = total − completed, clamped only for display; an invalid underlying count is a test failure, not silently fixed.
6. Restored flags and reward receipts are monotonic. Current prop/group completeness may reverse.
7. Slot claims reflect committed occupants plus any reservation within the current synchronous transaction. Preview never claims a shelf. Last removal resets its claim.
8. No slot's accepted family/domain can create an impossible remaining arrangement. Author slot sections uniformly in each interchangeable family pool, or validate the remaining capacity before claiming mixed pools.
9. All objective IDs remain accessible, detectable when appropriate, and recoverable within authored boundaries. A final hidden unknown type cannot be placed inside inaccessible geometry.

## Deterministic generation

The guarantee is the initial manifest for a fixed seed + game/content/generator version, not the running physics simulation. Godot's [RandomNumberGenerator](https://docs.godotengine.org/en/4.6/classes/class_randomnumbergenerator.html) supports seeded sequences, but its implementation should not be treated as a permanent cross-engine format.

1. Normalize a entered seed by trimming surrounding whitespace; preserve case and internal text. Empty input creates a seed once and immediately displays/saves it. Limit input to 64 UTF-8 bytes and reject control characters. Do not use scene start time once the seed exists.
2. Derive independent streams using SHA-256 of a UTF-8 JSON array of strings in this exact order: `[generator_version, content_hash, seed, section_id, stream_name]`, serialized with no optional whitespace. Stream names are `litter`, `props`, `piles`, `dirt`, `buried`, `rescue` and `valuables`. This avoids ambiguous delimiter concatenation when a seed contains punctuation. Use the first 15 hexadecimal digits as a positive 60-bit RNG seed. Pin the serialized bytes and resulting hash in a golden fixture, including Unicode and punctuation seeds.
3. Sort catalog IDs and authored anchors explicitly. Use integer weights, stable traversal and exact section/type quotas. Never depend on filesystem or Dictionary iteration order or a global randomized RNG.
4. Choose among authored, collision-checked placement anchors. A pose is stored in the content resource; use millimetre coordinates and fixed orientation indices in the manifest. Do not scatter randomly and let physics settle to establish the starting layout.
5. Piles use multiple authored stable layer patterns with individual item IDs. Reserve clearances per item's collision profile; do not embed inaccessible trash inside decorative rubbish-pile meshes. A bounded search failure reports the section/anchor conflict and aborts generation instead of silently dropping items.
6. Home section and item ID derive from stable section ID and spawn ordinal. Dirty counts, rescue choices and optional valuables use their separate streams. IDs never change when the player moves an item.
7. Canonicalize sorted manifest rows, serialize transforms as integer fields and hash that representation. Store the full initial manifest with the run save, plus runtime records. Replay creates a new run ID with the same initial manifest.
8. Validate exact quotas, unique IDs, reachable pickup anchors, correct bag/tool access progression, legal water depths, and enough prop destinations before presenting the run.

Generation should be based on curated anchor packs for each family/zone; use a small authoring utility only where hand-authoring hundreds of equivalent litter anchors is wasteful. Its output becomes versioned authored data. Cosmetic fish motion and water waves use separate timing and cannot consume gameplay RNG streams.

## Input and context

Godot [InputMap](https://docs.godotengine.org/en/4.6/classes/class_inputmap.html) supplies shared actions, and [controller support](https://docs.godotengine.org/en/4.6/tutorials/inputs/controllers_gamepads_joysticks.html) provides device mappings. A remapping UI, persisted overrides, changing prompts, focus navigation and table interaction still require implementation. Mouse delta and stick look need distinct sensitivity handling.

| Action | Keyboard/mouse default | Controller default |
|---|---|---|
| move / look | WASD / mouse | left / right stick |
| primary | LMB | right trigger |
| throw | RMB | left trigger |
| interact | E | west face button (X on Xbox) |
| jump / swim up | Space | south face button (A) |
| crouch / swim down | Ctrl | east face button (B) |
| sprint | Shift | left stick press |
| switch equipped tool | Q or 1/2 | right bumper |
| select held prop | mouse wheel | left bumper |
| booklet | Tab | View/Back |
| scanner pulse | F | right stick press |
| pause | Escape | Menu/Start |
| UI accept / cancel | Enter or click / Escape | A / B |
| table bin previous/next | 1–4 or bin click | LB / RB |
| table focus / select | arrows / Enter | D-pad / A |

Selected held prop controls which item LMB places; RMB always throws latest pickup among current hands. Tool switching cannot silently stash held props. E handles stations, containers and optional riding, while LMB handles objects/tool use/placement.

Context priority: pause/settings → booklet/shop → table → results → world. Only the active context consumes actions. Cancel exits one level, releases mouse capture appropriately and requires a fresh button edge before world actions. Table controller mode uses spatial grid focus and bin cycling; mouse dragging is an alternative, not mandatory for controller play. Remap physical keys, gamepad buttons and signed axes with conflict detection per context; keep a restore-defaults route and never leave the user without cancel/confirm.

## Physics, presentation and scale

Use simple convex/primitive collision shapes. [RigidBody3D](https://docs.godotengine.org/en/4.6/classes/class_rigidbody3d.html) supplies impulses, sleeping and freeze controls. Active bodies receive impulses; frozen hand/placement views animate separately. Do not continuously teleport an active body to the hand or tween its physics scale.

ItemViewManager owns synchronization of WORLD physics poses back to records for both loose items and disposal bags. Capture current transforms, linear/angular velocities and sleep state at a consistent physics boundary before snapshotting or demoting a view; also retain the final resting pose when a body sleeps. Synchronize the player's transform/velocity and breath state at that boundary. Saving only the last pickup/throw transform would rewind objects that have since rolled or sunk. Use the engine's physics-state access where needed; keep sleeping items free of per-frame scripts. Rebuild loaded bodies frozen, apply poses/velocities, then resume only after all owners and views exist. This preserves a snapshot, not deterministic future physics trajectories.

Start with sleeping bodies and shared meshes/materials, disabled script processing for idle items, and static world colliders. Measure P07 before adding a renderer rewrite. If full-scale draw/physics cost misses budget, P28 batches distant resting small litter per cell/mesh/material with MultiMesh and promotes nearby cells back to normal item views. IDs remain in ItemStore throughout. [MultiMesh](https://docs.godotengine.org/en/4.6/classes/class_multimesh.html) is for repeated rendering; it is not inventory, per-item selection or physics. Per-cell batches keep culling useful. Do not batch held, highlighted, slotted, falling or targetable near items.

Collision layer contract: 1 world, 2 player, 3 loose items, 4 fixed interactive props/stations, 5 slot/bin trigger areas, 6 water areas, 7 rescue targets. Mask raycasts against world plus target layers; stop at world occluders. Loose items collide with world/items; player movement ignores tiny litter to avoid standing on cans. Large furniture has player-blocking collision when dropped/slotted. Distinguish these profiles in definitions, not magic names. Sensors do not collide physically.

Default feel: 0.12 s poke response, 0.18–0.30 s pickup travel, 0.25 s placement travel, visual pulse 1.00→1.08→1.00 in 0.25 s, group sweep 0.8 s. Tune within P27 without changing ownership semantics. Outline only the hovered eligible target, white with a small dark backing for bright sand; hide through walls. Use an inverted-hull visual material initially and test thin/open meshes. Use per-instance shader parameters or duplicated effect materials so highlighting one object never changes all copies.

Keep the existing Compatibility renderer as the initial baseline. Its [renderer feature support](https://docs.godotengine.org/en/4.6/tutorials/rendering/renderers.html) differs from Forward+. Use local stain mesh patches rather than relying on `Decal`, which is [unavailable in Compatibility](https://docs.godotengine.org/en/4.6/tutorials/3d/using_decals.html). Water depth code must respect [Compatibility's clip-space convention](https://docs.godotengine.org/en/4.6/tutorials/shaders/advanced_postprocessing.html); test the supplied converted shader rather than assuming it is portable.

## Save format and atomicity

Use ordinary typed-to-JSON dictionaries via native JSON/FileAccess. This is local persistence, not an anti-cheat format. Do not deserialize arbitrary Objects, execute save-provided scripts, or accept resource paths from save files; IDs resolve through the validated catalog. Native [FileAccess](https://docs.godotengine.org/en/4.6/classes/class_fileaccess.html) supports files in `user://`; exported gameplay resources should use ResourceLoader instead.

Save root: `user://saves/<beach_id>/<run_id>/<slot_id>/`. Names shown to players are metadata, not filesystem paths. Validate IDs against a bounded allowed character set. Autosave has its own slot; manual slots do not overwrite it. Each slot has alternating generation A/B files containing sequence, schema, content hash, payload and checksum. Write/flush/close the inactive generation through a temporary file, validate it, then replace only that generation. Keep the previous valid generation until the new one is usable. Load highest valid generation, falling back with a clear message. Handle disk-full, corrupt/truncated files and denied writes without claiming success or discarding live state. No filesystem scheme can promise survival of every storage hardware failure.

Snapshot all item/bag/container/player state plus partial sorting, bin assignments, open shelf claims, dirt, rescues, recovery piles, discoveries, purchases, wallet, rewards, restored sections, active timer and original completion receipt. Store logical positions of slotted/table/held things by owner/slot; WORLD items and disposal bags retain synchronized physics poses/velocities. Save after action finalization and physics synchronization, including when pause has stopped simulation. A manual save while dragging cancels the transient drag back to its current logical cell; a placement tween resolves to its already committed slot. Store the player's world pose, not the overhead sorting camera transform. Reopen loads in world view at that valid pose with transient UI closed and all station contents preserved. Save before quit must finish successfully; otherwise offer retry or explicit quit without saving.

Start with synchronous writes. If P28 later introduces background writes, keep at most one write per slot in flight and prevent an older snapshot from overwriting a newer one. Save-and-quit waits for its own snapshot sequence to be persisted, not merely its run revision: movement and elapsed time can change without an item transaction. Validate a candidate load into temporary plain records before replacing the live run. A rejected load leaves the current run and its saves intact.

Default autosave: every 60 seconds of active play and after collection, sale, purchase, faint, restoration and first completion (coalesce simultaneous changes). Settings are a separate ConfigFile and survive new runs. Incompatible newer schema/content is rejected with explanation; missing known art falls back to a cube, but missing objective definitions must not silently delete saved items. P24 must provide explicit migrations if it changes an already shipped schema.

## Future multiplayer and leaderboards — preparation, not implementation

The concrete local mutation methods become host-authoritative operations later. Stable item/player/run IDs, clear owners and synchronous transactions are the preparation needed now. Do not synchronize 5,700 transforms continuously. A future host sends the initial manifest/hash plus current records and only dynamic deltas near players; late join applies a consistent snapshot then later revisions. Concurrent pickup/slot claims are checked on the host, with one accepted action and a rejection to the loser. Godot's [high-level multiplayer API](https://docs.godotengine.org/en/4.6/tutorials/networking/high_level_multiplayer.html) is the native starting point for that later work.

Future sharing toggles apply independently to wallet, skill/tool ownership and bag inventory; world cleanup/restoration is always shared. Preserve personal records even if future pooling is enabled. Sharing changes with occupied bags need an explicit reconciliation rule before that feature ships. Never duplicate wallet balances when toggling. Attribution fields make later payout policy possible, but do not implement shared menus or fake online UI now.

Record local result fields now: beach/content/generator version, seed/manifest hash, required total, collected waste, sorted props, active seconds, participant IDs/count (one), settings/ruleset, faint count, correctness counts and completion receipt. Future leaderboards must partition by seed/version/ruleset/trash total/player count and define whether count means maximum concurrent players or all participants. Local clocks, saves and seeds alone do not prevent cheating; ranked submission/authentication/validation is a later design, not a claim of this release.
